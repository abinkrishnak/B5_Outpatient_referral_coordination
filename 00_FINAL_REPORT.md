# PE6201 A2 — Problem B Report
## 1. Why an agent
Our outpatient referral coordination problem sits at Rung 7: Agent, but we deliberately keep deterministic work below the agent boundary. A plain language model at Rung 1, or a structured prompted response at Rung 2, cannot access current referral, patient, rule and appointment-slot records. RAG at Rung 3 is also not the right core design because our authoritative sources are structured systems of record rather than a document corpus. Rungs 4 and 5 remain useful: deterministic tools perform fixed checks, while conditional workflow logic enforces the order of red-flag, specialty, mandatory-test and duplicate-appointment checks. Rung 6, agentic retrieval, allows the model to choose which structured lookup to call next, but retrieval alone cannot complete the task. At Rung 7, the agent can observe tool results, choose the next action, repeat slot searches when necessary, and propose a gated real-world booking action.
The workflow test shows why a fixed sequence is insufficient. The appropriate next step depends on what the system observes. A referral with a red flag or missing mandatory test must stop before any slot search, while an eligible referral may require several queries before a suitable appointment is found. The ground-truth and machine-speed test also supports this design. Authoritative facts come from structured referral, patient, specialty, urgency, contact and clinic-slot records. Tools retrieve these facts at machine speed, while the model handles routing and explanation. Human confirmation remains mandatory before book_slot because booking changes an external appointment state and referral text is untrusted input.
Reliability also argues for a deliberately small agent. Our selected live-model baseline passed 51 of 60 trials, giving end-to-end reliability (P=0.85). With a typical successful run of (T=4) model turns, the assignment approximation gives (s=P{1/T}=0.85{1/4}approx0.960). At the same estimated per-turn reliability, three turns imply about 0.885 end-to-end reliability, whereas eight turns imply about 0.722. This is diagnostic rather than causal, because turns are not truly independent, but it explains why we minimise unnecessary turns through early stopping and parallel independent lookups.
For us, “good” therefore means retrieving ground truth before deciding, stopping at the first safety or completeness failure, searching only valid urgency windows, never booking without explicit confirmation, and recording the decision, evidence, operational metrics and guardrail events.
## 2. The tool layer

This project started with six candidate tools. Leave-one-out ablation on the five core tools (get_referral, lookup_patient, check_referral_criteria, get_clinic_slots, book_slot) showed that removing any one caused the case to fail or changed the baseline decision path (see table). Each performs an essential, non-substitutable function and is retained.
The most important neighbouring pairs to distinguish are get_referral vs. check_referral_criteria, and get_clinic_slots vs. book_slot. In the first pair, one retrieves raw facts while the other evaluates those facts against hospital protocol. In the second, one is a read-only search and the other an irreversible write. Clear parameter/return definitions reduce the model's risk of picking the wrong tool, and book_slot stays behind a confirmation gate since it is the only externally-effective action.
as_of was removed as a standalone tool because it was called zero times in the six-tool baseline. After folding the evaluation date into the compulsory get_referral response, the five-tool candidate produced no execution errors, no decision changes, and preserved full date information. So we removed a redundant interface, not the date itself. Tool-description length dropped from 3,916 to 3,606 characters/turn (−310), a proxy for prompt cost showing that an unused tool still consumes context and widens the model's choice space.

For get_clinic_slots, V1 typed specialty/band as plain str, so a typo like "OPHT" silently returned an empty list, indistinguishable from a fully-booked clinic. V2 constrains both with runtime validation; an invalid value now returns a structured invalid_slot_query observation naming permitted values instead of failing silently. This is a poka-yoke: it makes that failure class structurally impossible rather than merely discouraged.
Measured on Gemini 2.5 Flash-Lite, V1 scored 49/60 (81.7%), with 468,537 input tokens and a cost of $0.05153. V2 scored 48/60 (80.0%), using 434,084 input tokens and costing $0.04866. This represents 7.4% fewer input tokens and 5.6% lower cost, while the 1.7-point pass-rate gap is too small to claim a quality difference. We keep V2 because it converts a latent silent failure into a catchable error, independent of the cost saving.
A second poka-yoke: as_of was dropped from the callable tool registry and instead injected directly into the system prompt as a fixed EVALUATION CLOCK line, computed once per run. This removes the failure mode where the model forgets to call as_of and defaults to date_received. The date is now an environmental fact present before the first token, not dependent on a tool call succeeding.
Our dependency rule: two calls share a turn only if neither depends on the other's output and both are computable from what's already known. On REF-5602: get_referral runs alone (turn 1); check_referral_criteria and lookup_patient share turn 2; the two get_clinic_slots queries share turn 3; book_slot runs alone, last. This reduced 6 sequential turns to 4 parallel turns, cutting input tokens from ~42,000 to ~24,000 (−42.9%) and cost from $0.004536 to $0.00264, savings from fewer prefix re-sends, not less work.



## 3. What the evidence showed
D4 and D5 evidence shows that the system is reproducible, but model reliability varies. The frozen evaluation set contains 40 isolated referral cases: 30 ordinary cases and 10 negative cases. Each ordinary case ran once and each negative case ran three times, giving 60 trials per model. The answer key contains 30 book, 3 request_information and 7 escalate outcomes, with no missing or extra labels. Scripted regression passed 60/60, confirming the fixture data, routing logic, guardrails and harness. A separate human review of ten selected records found 10/10 required-evidence completeness and 10/10 safety outcomes; early-exit compliance was 9/10 because REF-5590 made an avoidable post-red-flag slot lookup. This judgement check is distinct from automated code checking.
The V2 live battery used the same data, contract, temperature, guardrails and trial schedule across five model families. DeepSeek Chat V3 achieved 51/60 (85.0%), Gemini 2.5 Flash 49/60 (81.7%), Claude Haiku 4.5 48/60 (80.0%), Llama 3.3 70B Instruct 45/60 (75.0%), and Mistral Small 24B 22/60 (36.7%). Thus, models diverged most on negative cases, tool-use discipline and explicit evidence in final reasons. Mistral was the cheapest raw API option but the least reliable, while DeepSeek had the highest pass rate and is the recommended model in this comparison.
The negative cases caught red flags, missing tests, duplicate future appointments, specialty mismatches, unavailable slots and hostile free-text instructions. REF-5590 also exposed a label-policy conflict: the safe protocol stops before slot lookup after a red flag, while the label requests proof that a slot existed and was not taken. We retained the safe behaviour and reported the conflict rather than hiding it.
## 4. What it costs
DeepSeek Chat V3 has the lowest expected cost in our final five-family comparison, although Mistral has the cheapest API usage. Our baseline follows the Class 5 escalation model: measured input and output tokens at dated list prices, expected human fallback, and fixed monthly cost. We reuse the notebook's three cost functions. We assume ten minutes per failed referral at US$55 per hour, approximately US$9.1667, retaining full precision in calculations. We multiply per-referral costs by 4,000 and then add fixed monthly costs.
DeepSeek passed 51 of 60 automated checks. Its 417,556 input and 21,236 output tokens yield a list-price inference cost of US$0.002094 per referral. Expected fallback adds US$1.375, giving US$1.377094 per referral and US$5,508.38 monthly. These are benchmark-based estimates, not validated clinical costs. Thirty ordinary cases run once and ten negative cases run three times, so the test weighting does not represent hospital prevalence.
We assume no additional paid tool, retrieval or monthly infrastructure services for the current prototype. Production maintenance, recurring evaluations, equipment and routine clinical escalation labour are unmeasured and excluded. The saved DeepSeek API charges total US$0.097416; they are kept separate from the US$0.125625 list-price baseline. Different routes or billing treatment may explain differences, but without paired tests we claim neither caching savings nor a measured reasoning-token adjustment.
At success rates of 75%, 85% and 95%, DeepSeek's monthly baseline is US$9,175.04, US$5,508.38 and US$1,841.71. A ten-percentage-point change therefore moves monthly expected fallback by US$3,666.67. Mistral would need approximately 84.98% success to match DeepSeek's expected cost, versus its observed 36.67%. This comparison is conditional on the observed pass rates and does not establish statistical superiority.

## 5. The two failures
We reproduced two different failures from the working agent. First, removing action de-duplication created a repeated-slot-query loop for REF-5602. The working run returned the correct book decision in 4 turns and 6 tool calls, including 2 slot queries. The broken run still returned book, but required 6 turns and 10 tool calls, including 6 slot queries. Tokens rose from 21,600 to 38,640 and cost from US$0.002340 to US$0.004116. Instrumentation detected the failure through turns, tool calls, slot queries, tokens and cost, even though decision accuracy did not change. Restoring the guard returned the original behaviour. This was correctly fixed in the code/control layer; a prompt-only fix would not reliably stop repetition.
The second failure was an invalid tool query. Under the weaker interface, a value such as OPHT could look like an empty search result and lead to an incorrect escalation. The V2 closed-set contract validates specialty and urgency values and returns an explicit invalid_slot_query result with allowed values. This belongs to the tool-interface layer, so schema validation was the appropriate fix. Both failures were run on the scripted backend and their before/after evidence is committed.
## 6. What we would not deploy
We would not deploy the current prototype as an autonomous clinical booking system. The live battery shows substantial model variation, from 85.0% for DeepSeek Chat V3 to 36.7% for Mistral Small 24B, and even the human review found one avoidable post-red-flag slot lookup. The evaluation set is also a benchmark rather than evidence of real hospital prevalence or clinical validation.
We considered, but did not build, a multi-agent architecture in which separate agents could independently review referral safety, eligibility and booking before a final coordinator acts. Such separation might catch disagreements or reasoning errors before an appointment is booked. However, it would add model calls, coordination steps, latency and cost, while creating additional failure points. Our reliability analysis already shows the penalty associated with unnecessary turns. We therefore stayed with a single ReAct agent surrounded by deterministic criteria checks, guardrails and an explicit human confirmation gate for the irreversible book_slot action.
